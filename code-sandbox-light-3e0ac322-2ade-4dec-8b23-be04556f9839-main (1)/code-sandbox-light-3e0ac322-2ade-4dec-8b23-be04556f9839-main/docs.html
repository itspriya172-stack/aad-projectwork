1. Problem statement

Students preparing for several exams simultaneously must decide what to study, when, and for how long. Each topic has a different difficulty, a different weight in the exam, an estimated study time, and a hard deadline (the exam date). The student has only a limited number of study hours per day, and some topics can only be understood after others (prerequisites).

Manual planning is error-prone: urgent topics are forgotten, easy topics are over-studied, and unfinished work is never re-planned. We model this as a deadline-constrained scheduling problem: given a set of n topics with value (priority), processing time (hours) and deadlines, produce a timetable that maximises the total priority studied, never exceeds the daily hour budget, never schedules a topic after its exam, honours prerequisites, and tells the student clearly when the available time is insufficient.

The general version (maximising weighted completed jobs on a single machine with deadlines and arbitrary processing times) is NP-hard — it contains the 0/1 Knapsack problem as a special case. The project therefore uses a Greedy heuristic driven by a priority queue for the schedule itself, and Dynamic Programming (0/1 Knapsack) to choose the optimal subset of topics when time is short.

2. Objectives and scope

Objectives

  • Compute a numerical priority for every topic from its importance, difficulty and days remaining until the exam.
  • Generate an optimised day-by-day timetable within the user's daily study-hour limit.
  • Respect topic prerequisites and never schedule a topic on or after its exam.
  • Detect and report insufficient time; use DP to decide which topics to commit to.
  • Track progress (pending / in-progress / completed) and automatically reschedule unfinished work.
  • Visualise progress with charts, progress bars and statistics in a clean, responsive UI.
  • Genuinely implement and analyse the DAA concepts: Greedy, Sorting (Merge Sort), Priority Queue (Binary Max-Heap), Dynamic Programming (0/1 Knapsack), and Graph topological ordering (Kahn's algorithm) for prerequisites.

Scope

  • In scope: single student, multiple subjects/topics, daily hour budget, slot-based timetable, persistence of plans, progress tracking, documentation and tests.
  • Out of scope: multi-user accounts, calendar sync, learning-rate modelling (spaced repetition), server-side authentication.

6. Algorithms and pseudocode

6.1 Priority formula

Priority(t, day) = (2 · Importancet + Difficultyt) × Urgency(daysLeft)
Urgency(d) = 1 + 10 / (d + 1)
  • Importance is weighted twice because exam marks depend more on what is asked than on how hard it is.
  • Difficulty adds weight so hard topics are started earlier (they need more consolidation time).
  • Urgency is hyperbolic: 11× the day before an exam, 2.25× one week out, ≈1.3× one month out. It never reaches zero, so distant exams are still studied when nothing urgent remains. A topic whose exam has passed gets priority 0.
  • Priorities are recomputed every simulated day, so a topic naturally climbs the heap as its exam approaches.

Example: Dynamic Programming (I=5, D=5) with 7 days left → (10+5) × (1+10/8) = 15 × 2.25 = 33.75. Set Theory (I=3, D=2) with 19 days left → 8 × 1.5 = 12.0.

6.2 Binary Max-Heap (priority queue)

class MaxHeap(compare):
    a ← []
    procedure PUSH(x):            // O(log n)
        append x to a;  i ← |a|−1
        while i > 0 and compare(a[i], a[parent(i)]) > 0:
            swap a[i], a[parent(i)];  i ← parent(i)
    procedure POP():             // O(log n)
        top ← a[0];  a[0] ← a.removeLast();  SIFT-DOWN(0);  return top
    procedure SIFT-DOWN(i):
        loop: l ← 2i+1; r ← 2i+2; best ← i
              if l < n and a[l] ≻ a[best]: best ← l
              if r < n and a[r] ≻ a[best]: best ← r
              if best = i: break
              swap a[i], a[best]; i ← best
    static HEAPIFY(items):      // O(n) — Floyd's bottom-up build
        a ← items;  for i ← ⌊n/2⌋−1 downto 0: SIFT-DOWN(i)

6.3 Merge Sort (Divide & Conquer) — ranking topics

function MERGE-SORT(A, compare):
    if |A| ≤ 1: return A
    mid ← ⌊|A|/2⌋
    L ← MERGE-SORT(A[0..mid)),  R ← MERGE-SORT(A[mid..|A|))
    return MERGE(L, R)                   // stable: take from L when equal

// comparator used in the planner (ties broken deterministically)
function BY-PRIORITY-DESC(a, b):
    if a.priority ≠ b.priority: return b.priority − a.priority
    if a.daysLeft ≠ b.daysLeft: return a.daysLeft − b.daysLeft   // earlier exam first
    return b.remaining − a.remaining                         // bigger job first

Merge sort was chosen over quick sort because it is stable (two equal-priority topics keep their deadline order) and has a guaranteed Θ(n log n) worst case.

6.4 Prerequisite check — Kahn's topological sort

function DETECT-CYCLE(topics):
    indeg[v] ← 0 ∀v;  adj[u] ← []
    for each t with prerequisite p: adj[p].append(t); indeg[t]++
    Q ← all v with indeg[v] = 0;  visited ← 0
    while Q ≠ ∅: u ← Q.dequeue(); visited++
        for v in adj[u]: indeg[v]--; if indeg[v] = 0: Q.enqueue(v)
    return visited = |topics| ? NONE : { v | indeg[v] > 0 }       // O(V+E)

6.5 Greedy slot scheduler (core algorithm)

function GENERATE-SCHEDULE(topics, subjects, H, today):
    work ← { t : remaining(t) > 0 and daysLeft(t) > 0 }
    horizon ← max daysLeft over work
    cap ← ⌈H / 2⌉                                   // max hours per topic per day (pass 1)
    for day ← 0 to horizon − 1:
        for each t in work: t.priority ← PRIORITY(t, today + day)
        hoursLeft ← H
        for capped in [true, false]:                // pass 2 lifts the cap if time is left
            heap ← HEAPIFY({ t ∈ work : ELIGIBLE(t) })  // O(n)
            while hoursLeft > 0 and heap ≠ ∅:
                t ← heap.POP()                            // greedy choice: highest priority
                block ← min(t.remaining, hoursLeft, capped ? cap − givenToday[t] : ∞)
                EMIT slot(day, clock, clock+block, t)
                t.remaining −= block;  hoursLeft −= block;  clock += block
                if t.remaining = 0: for d in dependants[t]: if ELIGIBLE(d): heap.PUSH(d)
    unscheduled ← { t ∈ work : t.remaining > 0 }     // insufficient time
    return slots, unscheduled, warnings

function ELIGIBLE(t): t.remaining > 0 and t.daysLeft > 0 and
                     (no prerequisite or prerequisite.remaining = 0)

Greedy-choice property: at every slot we take the topic with the highest current priority. Because urgency is monotone in days-left and a topic's exam date never moves, the ranking between two topics of the same subject never changes; between subjects it changes only in favour of the nearer exam — exactly the behaviour a student wants. Prerequisites are handled Kahn-style: a dependant enters the heap only when its prerequisite has been fully scheduled, which guarantees ordering with zero extra sorting.

Why the per-topic cap? Without it the greedy would put all 5 daily hours on one topic. The cap of ⌈H/2⌉ forces at least two topics per day (better retention — interleaving), and a second pass without the cap guarantees no hour is wasted when only one topic is eligible.

6.6 0/1 Knapsack — Dynamic Programming topic selection

When Σ remaining hours > total budget B = H × horizon, not everything can be finished. We choose the subset of topics maximising total priority:

maximise Σ pi·xi subject to Σ hi·xi ≤ B, xi ∈ {0, 1}
dp[i][w] = max( dp[i−1][w], dp[i−1][w − hi] + pi ) if hi ≤ w
function KNAPSACK-SELECT(items, B):
    W ← B / slotSize;  n ← |items|
    dp ← (n+1) × (W+1) table of 0
    for i ← 1 to n:
        for w ← 0 to W:
            dp[i][w] ← dp[i−1][w]
            if hi ≤ w and dp[i−1][w−hi] + pi > dp[i][w]:
                dp[i][w] ← dp[i−1][w−hi] + pi
    // reconstruction
    selected ← ∅;  w ← W
    for i ← n downto 1:
        if dp[i][w] ≠ dp[i−1][w]: selected.add(items[i]); w ← w − hi
    return selected, dp[n][W]

Optimal substructure: an optimal selection from the first i items with budget w either excludes item i (then it is optimal for i−1, w) or includes it (then the rest is optimal for i−1, w−hi). Overlapping sub-problems: dp[i−1][·] is reused for every w, so memoising in a table avoids the 2n brute force.

In Greedy + DP mode the committed set becomes tier 0 in the heap comparator — the scheduler always prefers committed topics, and fills leftover hours with the rest "best-effort".

6.7 Rescheduling

Slots whose date is before today and that were not ticked off are "missed". Because the scheduler always starts from remaining = duration − hours_done, regenerating from today automatically carries every unfinished hour forward; missed topics are flagged rescheduled (↻) in the timetable. Cost O(S) over saved slots plus one regeneration.

With realistic inputs (n = 20 topics, D = 20 days, H = 5 h) the scheduler performs roughly 20 × (20 + 20·log 20) ≈ 2 000 elementary operations — instantaneous. Even n = 500, D = 365 is about 1.6 million operations, still well under a second in JavaScript.

Space detail

  • Work items: one object per topic — Θ(n).
  • Heap: array of at most n references — Θ(n), rebuilt per day (freed afterwards).
  • Output: at most 2k slots per day (two passes) — Θ(D·k).
  • Knapsack: Float64Array of (n+1)(W+1) doubles; for n = 20, W = 100 that is 2 121 × 8 B ≈ 17 KB.

Quality (not time) analysis of the Greedy scheduler: when the total hours fit in the budget (the common case) the greedy produces a complete, feasible schedule — every topic is finished before its exam, provided a per-subject EDF-style ordering exists. When time is insufficient the greedy drops the lowest-priority topics at the end, which may be sub-optimal in total value (see §9). This is why DP is offered as the selection step.

Worked counter-example (TC10)

Budget 10 h. Topics (priority, hours): A (60, 5h), B (50, 4h), C (50, 4h), D (10, 1h). Greedy-by-density picks B (12.5/h), C (12.5/h), then D → value 110, 9 h used. DP picks A + B + D → value 120, 10 h used. The planner shows this comparison live in Greedy + DP mode.

Conclusion of the comparison: the two approaches are complementary. The project uses DP for the selection sub-problem (where optimality matters and W is small) and Greedy for the sequencing sub-problem (where constraints are rich and the input changes daily).

12. Advantages, limitations and future enhancements

Advantages

  • Mathematically explainable priorities — the student sees the formula and the score for every topic.
  • Hard constraints (daily hours, exam deadline, prerequisites, no duplicate slot) are guaranteed by construction and verified by a validator.
  • Fast: polynomial greedy; DP only on the small selection problem.
  • Honest about infeasibility — reports exactly which topics are short and by how many hours.
  • Progress is persistent; rescheduling is a single click.

Limitations

  • Greedy sequencing is a heuristic: when time is insufficient it does not guarantee maximal total priority (mitigated by the DP selection step).
  • Priority weights (2:1, hyperbolic urgency) are fixed design constants rather than learned per student.
  • The knapsack treats topics as all-or-nothing; partial credit for a half-studied topic is not modelled in the selection step.
  • Single study block per day (start time + consecutive slots); breaks and multiple sessions are not modelled.
  • Static front-end persistence: no multi-user authentication.

Future enhancements

  • Spaced-repetition revision slots (Ebbinghaus forgetting-curve) scheduled after each topic is completed.
  • Fractional knapsack / weighted-interval DP to give partial value for partially studied topics.
  • Multiple daily sessions and break scheduling (interval partitioning).
  • Learning the importance/difficulty weights from past exam results.
  • Calendar export (iCal) and notifications.

13. Conclusion

The Smart Study Planner shows how classical Design-and-Analysis-of-Algorithms techniques solve a real student problem. A Greedy algorithm driven by a binary max-heap priority queue builds a feasible, deadline-aware timetable in O(D·n log n); merge sort ranks topics stably for the dashboard; Kahn's topological sort validates prerequisites; and 0/1 Knapsack dynamic programming selects the optimal set of topics when the available hours are insufficient — the exact case where greedy is provably sub-optimal. Each algorithm is implemented from scratch, instrumented (comparison and heap-operation counters), analysed for time and space in best, average and worst case, and verified by an automated test-suite. The result is a working application with a modern, responsive interface and a complete analytical report suitable for a college-level DAA submission.
